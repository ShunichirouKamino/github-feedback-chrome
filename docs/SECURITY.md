# Security Countermeasures

The threats github-feedback is designed against, and how each is mitigated. Every countermeasure links to its implementation.
Implementation links are permalinks pinned to [`45b045b`](https://github.com/ShunichirouKamino/github-feedback-chrome/tree/45b045bcc5f7a705a085cd1c90b1e35229a0a3a5), so later code changes do not shift the lines (update this document whenever you change a countermeasure).

## Assumptions

| Item | Details |
|---|---|
| Assets | Content of internal pages (URLs, DOM, logs, screenshots), the target repository, the user's GitHub session |
| Untrusted | The target page (it shares the DOM with the extension, and MAIN-world scripts can be tampered with), all data taken from the page, input on the settings page |
| Trusted | The extension's isolated world and service worker, the configured GitHub host |
| Principles | Decide and validate in the service worker. Sanitize page-derived values before use. Least privilege. A human always submits |

## Countermeasures

## Accepted risks

| Risk | Why it is accepted | How users are informed |
|---|---|---|
| Redaction is heuristic and incomplete; anything visible in a screenshot cannot be masked | Free-form data cannot be classified perfectly. The workflow assumes a human reviews the content on GitHub before submitting | README, the screenshot-range note on the settings page |
| The screenshot is uploaded to GitHub as soon as it is pasted (it stays even without submitting) | Same behavior as a normal GitHub image attachment. Countermeasures 1, 3, and 9 make sure the target is correct | README |
| The page can read and spoof its own diagnostics | What is recorded is the page's own logs and requests, and the page can already print any string with `console.error`. The body isolates it as unverified data | Note in the issue body |
| The page can remove the extension UI to make it unusable | An availability issue only; no information leaks | — |
| The title is in the URL | It is text the user writes on purpose for publication | — |
